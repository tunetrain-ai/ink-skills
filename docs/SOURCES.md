# Upstream sources

This catalog is written by hand against the packages listed in
[`data/ecosystem.json`](../data/ecosystem.json), which is the single source of
truth for the compatibility tables below and for the matrix in
`skills/ecosystem/ink-ecosystem-overview/SKILL.md`. Both are generated from it
by `npm run index` — edit the data file, not the tables.

`.github/workflows/refresh-upstream.yml` runs weekly, re-resolves every
package's `latest` version, peer ranges and engines from the npm registry, and
— when anything has moved — pushes the refreshed fields to the
`chore/refresh-upstream` branch and opens (or updates) a tracking issue. That
is a signal, not a fix: it never changes a package's `status`, a skill, or a
`metadata.ink` stamp.

> **Author against the installed `.d.ts` files, not the readme.** A package's
> GitHub readme can be ahead of what is published to npm: props documented on
> `master` may not exist in the shipped types. `npm run typecheck` is what
> catches this. Treat a readme as a lead to verify, never as a source of truth
> by itself.

## How a package's status is decided

A declared peer range only says what the author *intended*, and it is wrong in
both directions: `ink-table` and `ink-markdown` declare ranges that include
Ink 8 yet cannot be loaded on it, while `ink-tab` and `ink-scroll-view`
declare ranges that exclude it yet render fine. So each package is probed:

1. **Install** next to the current Ink and React with strict peer
   dependencies (`npm install <pkg>`). A peer conflict (`ERESOLVE`) means the
   range excludes the current Ink.
2. **Import** it under Node ESM (`import('<pkg>')`, never `require`). Ink is
   ESM with top-level `await`, so a CommonJS package that `require()`s it
   throws `ERR_REQUIRE_ASYNC_MODULE`. A package that bundles its own copy of an
   old Ink can crash here too.
3. **Render** a minimal tree on Ink 8 and read what it drew. For a
   peer-excluded package install it with `--legacy-peer-deps` first.

These probes are executable. `tests/claims/ink-ecosystem-overview.test.mjs`
runs all three for every package in the data file — the install offline, with
stub packages that carry the real peer ranges, so npm itself decides — and
fails when a status or a note stops being true.

Statuses (`status` in the data file):

| Status | Meaning |
| --- | --- |
| `core` | Ink itself, or a package this catalog is built on. |
| `works` | Installs with strict peers and renders on the current Ink. |
| `peer-excluded` | The declared peer range excludes the current Ink. Installing needs `--legacy-peer-deps`; the note says what works at runtime. |
| `untested` | Installs, but its behavior on the current Ink was not exercised. (No package has this status today; the claim tests have no case for it, so a package given it fails them.) |
| `broken` | Fails to load or crashes on the current Ink / React. |
| `avoid` | Exists but is the wrong package for what the skills document. |

`npm run validate` cross-checks `works` and `peer-excluded` against the
registry-derived peer range, so a refresh PR that moves a range fails CI until
someone re-probes the package and flips its status. A render proves the package
loads and draws; what it does with input or a resize is proven only where a
skill says so.
